01

The system at a glance

Cloudflare DNS points the subdomain to Vercel. Vercel serves the frontend and forwards API requests to a hosted Python service over HTTPS. The API authorizes users and submits jobs; a worker performs generation. A persistent database and object storage preserve the results. GitHub deploys both parts.

This design deliberately runs generation on a hosted Python backend outside Vercel. Vercel supports Python functions, but the current long-lived server, background thread and disk-based builds are not a drop-in fit. A function-based alternative would require its own durable orchestration, external storage and dependency/time-limit validation.

03

What happens after Generate

The browser receives a job ID immediately. Python generation happens in the background; the browser checks progress and loads only a completed result matching the current draft. The flow includes login, invalid input, waiting and failure recovery.

Editable Mermaid flowchart source
flowchart TB
    START([Open design.yourdomain.com]) --> LOAD[Load studio and browser 3D viewer]
    LOAD --> AUTH{Valid signed-in session?}
    AUTH -->|No| LOGIN[Sign in]
    LOGIN --> AUTH
    AUTH -->|Yes| EDIT[Enter plot details and arrange rooms]
    EDIT --> SEND[POST /api/generate with project revision]
    SEND --> VALID{Allowed project and valid input?}
    VALID -->|No| FIX[Show permission or validation error]
    FIX --> EDIT
    VALID -->|Yes| ACCEPT[Persist job and return HTTP 202 with job_id]
    ACCEPT --> QUEUE[Coordinator schedules durable job]
    QUEUE --> RUN[Python generates plan, scene and exports]
    RUN --> RESULT{Generation successful?}
    RESULT -->|Yes| SAVE[Store artifacts and mark job done]
    RESULT -->|No| ERROR[Persist error or retry transient failure]
    ACCEPT -->|Browser polls GET /api/jobs/id| POLL{Persisted job status?}
    SAVE --> POLL
    ERROR --> POLL
    POLL -->|Queued or running| WAIT[Display progress and wait briefly]
    WAIT --> POLL
    POLL -->|Error| EXPLAIN[Show actionable error and keep draft]
    EXPLAIN --> EDIT
    POLL -->|Done| OWNER[Verify result belongs to user and draft revision]
    OWNER --> FETCH[Fetch scene with authorized access]
    FETCH --> VIEW[Render walkthrough on user device with WebGL2]
    VIEW --> DOWNLOAD([Download PDF, DXF, GLB, IFC or ZIP])

API responsibilities

RequestProposed contract
GET /api/sessionReturn the authenticated session, app defaults and permitted capabilities. Use secure session handling rather than exposing one global write token.
POST /api/generateValidate input and ownership, persist the job, then return 202 with job_id. Accept an idempotency key to avoid duplicate work on a retry.
GET /api/jobs/{id}Return only that user's job: queued, running, done or error. Include progress and authorized result locations when complete.
Project save and loadAdd authenticated endpoints for persistent project revisions. These account-based storage endpoints are new work.
Scene and export accessAuthorize the user before serving private files or issuing short-lived URLs. Public sample files may be cached; session, job and private project responses must not be shared in a public cache.

Planning validation errors return to the user. Only transient infrastructure failures should be retried automatically, with bounded attempts. Store progress durably so a process restart does not silently lose accepted work.

04

From repository to remote access

This release flow applies to future application deployment work. The diagrams and guides themselves are reading material.

Editable Mermaid flowchart source
flowchart TB
    CODE[Application changes in GitHub] --> API[Deploy backend and worker to staging]
    API --> UI[Deploy frontend preview on Vercel]
    UI --> CHECK{End-to-end workflow passes?}
    CHECK -->|No| FIX[Fix application and repeat]
    FIX --> CODE
    CHECK -->|Yes| LIVE[Promote compatible backend and frontend]
    LIVE --> DNS[Set Cloudflare CNAME to Vercel target]
    DNS --> WATCH[Monitor API, jobs and downloads]
    WATCH -->|Regression| ROLLBACK[Restore previous compatible release]

  1. Select backend hosting and persistent storage

    Choose an always-available managed container host or VPS for the Python API and worker, plus a durable database and object storage. A VPS is one option; managed hosting can handle server operation. Avoid relying on a sleeping development laptop for production access.

  2. Adapt and deploy the backend first

    Implement authentication, project ownership, durable jobs and file publishing. Package the engine with a supported Python version and its locked dependencies. Expose an HTTPS API and health check, configure secrets on the host, and prove generation and restart recovery in staging.

  3. Prepare a static frontend output

    Publish the studio HTML, CSS, JavaScript, committed viewer bundle and intended public samples in a dedicated output directory. Exclude private builds, secrets, development dependencies and this documentation folder. Keep /samples/* and /demo/* working through packaged public files or explicit backend routes.

  4. Connect GitHub to Vercel

    Create the Vercel frontend project from the repository. Use the Other framework preset for the existing static frontend. Explicitly set its output directory and build/install commands; do not accidentally run the optional web/package.json lab build instead of preparing the studio assets.

  5. Connect the frontend and backend

    Configure /api/* rewrites to the hosted HTTPS API. Preserve path prefixes deliberately, permit the frontend origin at the backend, and validate the real user session on every backend request. Use secure cookies or tokens; a rewrite alone does not grant authorization. Disable shared caching for private API responses.

  6. Serve private results safely

    Update scene/export loading for authorized object-storage URLs or owned download routes. Configure CORS for scene JSON and assets fetched across origins. Public samples may be cached; /builds/* must retain ownership checks. Keep large file transfer out of ordinary function responses.

  7. Validate the Vercel preview end to end

    Use a staging backend and explicit allowed preview origin. Test login, generation, progress, scene loading and export downloads across both hosts. Avoid a broad wildcard origin policy just to allow every preview deployment.

  8. Attach your existing subdomain

    Add design.yourdomain.com in Vercel domain settings. Copy Vercel's exact CNAME target to Cloudflare DNS, choose DNS only, and remove only conflicting records for that subdomain. Verify domain ownership and HTTPS; the root website can stay on its existing host.

  9. Release and operate both services

    Promote compatible API and frontend versions, invite initial users, and monitor API latency, job failures and storage. Keep coordinated rollback instructions, database backups and generation limits. Configure future application deployments to ignore changes confined to this documentation folder.

Illustrative API routing configuration

Replace the hostname with your deployed backend. This is a proposed configuration example, not a deployment file installed in this repository.

{
  "rewrites": [
    {
      "source": "/api/:path*",
      "destination": "https://api.yourdomain.com/api/:path*"
    }
  ],
  "headers": [
    {
      "source": "/api/:path*",
      "headers": [
        { "key": "Cache-Control", "value": "private, no-store" },
        { "key": "x-vercel-enable-rewrite-caching", "value": "0" }
      ]
    }
  ]
}

The backend must also return private/no-store cache headers and enforce authentication. This keeps both the frontend and backend /api/ prefixes; adjust the destination only if your backend contract differs.

Hosting and budget

Budget for Vercel, Python hosting, a database and object storage. Vercel Hobby is for personal non-commercial use; choose the appropriate paid plan for a commercial app. Optional AI adds provider usage. Capacity and pricing should follow measured generation workload.

Work required in this repository

The existing engine and viewer can be reused. These are the changes that turn a local studio into an application for independent remote users.

Existing projectRequired web adaptation
floorforge/server.pyThe server binds to 127.0.0.1 and allows only local hosts and origins. Add a production API adapter with explicit HTTPS origins and proxy handling; bind the container's exposed service to its configured interface. Keep local operation available.
Shared server stateReplace the process-wide session token, latest build, job dictionary and optional AI configuration with authenticated user ownership. Check ownership on every project, job and artifact request.
Generation workerThe current worker accepts one active build and returns BUSY for another. Implement a persistent queue, job IDs, idempotent submission, bounded concurrency and retry handling. A managed coordinator does not supply this application logic automatically.
floorforge/pipeline.pyReuse the deterministic planner and exporters. Use temporary disk for working files, then publish completed artifacts atomically to persistent storage. Record artifact hashes, the input plan hash and draft revision.
web/project-workspace.jsBrowser checkpoints currently live in localStorage. Add account-based project saving for access across devices; retain local draft recovery.
web/app.jsPreserve the asynchronous Generate → poll → load workflow. Adapt session handling and result URLs, show queued work, and reject results for an older edited draft.
Samples and downloadsKeep public sample routes available. Protect private build files, use short-lived download grants, and configure CORS when the viewer fetches scene files from a separate storage origin.
Optional AILaunch with AI disabled unless needed. If enabled later, keep provider secrets on the server and scope settings and spending to the correct user. Never publish secrets in frontend files or GitHub.
06

Before opening access to users

  • Open the live subdomain from a different internet connection and verify HTTPS, login and logout.
  • Use two accounts: each can save and reopen a project; neither can fetch the other's job or build files.
  • Generate two projects together and verify queued work, progress, successful exports and useful input errors.
  • Restart a worker during a job. Recover or report failure without losing the draft; completed files remain available.
  • Render the walkthrough and download the PDF, DXF, GLB, IFC and ZIP. Verify cross-origin scene requests if storage is separate.
  • Check a desktop browser and a phone. The 3D viewer needs WebGL2; the user's GPU determines rendering performance.
  • Verify old and new app versions agree on API and scene schemas; document rollback and database compatibility.

User experience

Open the link → sign in → design rooms → generate → explore → download. Python, Node and Blender are not installed on the user's device. A modern browser and WebGL2 are needed for the walkthrough.
