The recommended first launch

GitHub + Cloudflare + one Linux cloud server. The same server hosts the website, the Python API, a background generator and private project storage. You do not need to buy another domain or rent separate frontend and backend servers.

GitHub

Stores the source and reviewed releases. The server installs a selected release from it.

Cloudflare

Provides your domain routing, browser HTTPS and a tunnel to the cloud server.

Cloud server

Stays running when your laptop is off. Python creates the floor plans, models and exports here.

Provider recommendation: a DigitalOcean Basic, Regular, bundled Droplet with Ubuntu 24.04 LTS, x86-64, 2 vCPUs, 4 GiB RAM and 80 GiB disk. Start with Bangalore or Singapore if that configuration is available. This is an initial sizing proposal for the core generator; benchmark before promising capacity.

Name: myverandah.carekosh.com is short enough to share and matches the app's home-design theme. Alternatives are designyourhome.carekosh.com and homeatelier.carekosh.com. Subdomains are DNS entries under the domain you own, so these do not require separate domain registrations.

The current app is not yet ready for anonymous public generation. Its server is designed for localhost, uses a server-wide session token, and shares job state and the latest generated build. A tunnel or domain does not add visitor isolation. Complete the application work below before opening generation to everyone.

The current implementation is in floorforge/server.py: State, Handler.trusted(), /api/session, /api/jobs/... and /builds/.... This plan follows your choice of public access; a permanent invite-only Cloudflare Access gate would not meet that requirement.

How requests and designs travel

Visitor flow: open the URL → receive a private guest session automatically → enter plot size and rooms → submit a design → see queue/progress → open the matching 2D and 3D results → download the files. Guests need no Python installation, GitHub account or access to your computer.

First release: anonymous guest sessions with downloadable projects. Keep generated guest files for a clearly disclosed period, initially 24 hours. Offer a project JSON download so visitors can reopen their work. Permanent cloud saves and cross-device access can be added with user accounts later.

Steps 2–8 — deploy the reviewed public release

Account work and code work have different owners. You provide Cloudflare domain access, a cloud-provider account and billing, and an SSH key. The application developer implements Step 1, publishes the reviewed release and completes the server configuration. Never paste API keys, tunnel tokens or SSH private keys into this document or a public repository.

Step 2
Check the domain and prepare a release

  1. Open Cloudflare → select carekosh.com. Confirm the zone is Active and that Cloudflare manages its authoritative DNS. If bought elsewhere, follow the domain onboarding guide. Preserve existing DNS records for any website and email.
  2. Use the public name MyVerandah by Carekosh and the hostname myverandah.carekosh.com. Do not modify the root-domain website.
  3. Finish Step 1, review and publish its changes to GitHub. Record the exact full commit SHA of the release in rishabhrd09/FloorForge-2. Backend changes need the core checks plus meaningful session, ownership, restart and quota tests; a documentation-only skip-CI approach does not validate these runtime changes.

Step 3
Create the cloud server

  1. In DigitalOcean, choose Create → Droplets. Select a nearby available region, Ubuntu 24.04 LTS x86-64, and Bundled → Basic → Regular → 2 vCPUs / 4 GiB / 80 GiB. Name it myverandah-prod.
  2. Attach your SSH public key and enable monitoring. Select a backup option after reviewing its extra charge. Create the server and record its IP address.
  3. Attach a cloud firewall: allow inbound SSH TCP 22 only from your administrator IP, and no public inbound 80, 443, 8000 or 8080. Allow outbound traffic; the tunnel needs to reach Cloudflare, including port 7844. Keep provider-console recovery available if your administrator IP changes.

This step creates a paid resource. Provider details: Create a Droplet. Two vCPUs/4 GiB is a trial starting size, not a guarantee for arbitrary concurrent users or local AI models.

Step 6
Configure the local web proxy

Create /etc/nginx/sites-available/myverandah with the configuration below. This is for the new public application, which accepts the configured public Host and checks the real incoming HTTPS Origin. The existing local server would reject it.

nano /etc/nginx/sites-available/myverandah
Nginx configuration for the proposed public release 
limit_req_zone $binary_remote_addr zone=ff_generate:10m rate=3r/m;

server {
    listen 127.0.0.1:8080 default_server;
    server_name _;
    return 421;
}

server {
    listen 127.0.0.1:8080;
    server_name myverandah.carekosh.com;
    client_max_body_size 2m;

    # Only local cloudflared may supply Cloudflare's verified visitor IP.
    set_real_ip_from 127.0.0.1;
    real_ip_header CF-Connecting-IP;

    # Preserve Host, Origin, cookies and CSRF headers for app validation.
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto https;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_read_timeout 60s;

    location = /api/generate {
        limit_req zone=ff_generate burst=2 nodelay;
        limit_req_status 429;
        proxy_pass http://127.0.0.1:8000;
    }

    location / {
        proxy_pass http://127.0.0.1:8000;
    }
}

Enable it on this fresh dedicated server and validate:

ln -s /etc/nginx/sites-available/myverandah /etc/nginx/sites-enabled/myverandah
rm -f /etc/nginx/sites-enabled/default
nginx -t
systemctl enable --now nginx
systemctl reload nginx
curl -i -H 'Host: myverandah.carekosh.com' http://127.0.0.1:8080/healthz
ss -ltn

Confirm ports 8000 and 8080 listen only on 127.0.0.1. The Nginx IP limit supplements app-level guest quotas; it does not replace them. Keep generated files behind the app's authorization routes. Do not add a direct public alias for the data directory.

Proxy syntax reference: Nginx proxy module. HTTPS ends at Cloudflare; the short HTTP connection here stays on the same machine behind the tunnel.

Step 7
Connect Cloudflare Tunnel and the subdomain

Install Cloudflare's connector on the server using its official package repository:

mkdir -p --mode=0755 /usr/share/keyrings
curl -fsSL https://pkg.cloudflare.com/cloudflare-main.gpg -o /usr/share/keyrings/cloudflare-main.gpg
printf '%s\n' 'deb [signed-by=/usr/share/keyrings/cloudflare-main.gpg] https://pkg.cloudflare.com/cloudflared any main' > /etc/apt/sources.list.d/cloudflared.list
apt-get update
apt-get install -y cloudflared
  1. In Cloudflare, go to Networking → Tunnels → Create Tunnel. Name it myverandah-prod. Dashboard layouts can vary; some accounts show tunnels under Zero Trust.
  2. Select Linux/Debian and copy the connector service-install command shown in your dashboard. Run it on this server. It has the form sudo cloudflared service install <TUNNEL_TOKEN>. Treat the token as a secret and avoid sharing or committing it.
  3. Wait until the connector is healthy. Under Routes → Add route → Published application, set Subdomain: myverandah, Domain: carekosh.com, Path: blank, and Service URL: http://127.0.0.1:8080.
  4. Under additional HTTP application settings, set HTTP Host Header: myverandah.carekosh.com. Do not replace the browser's Origin with a localhost value.
  5. While staging, protect the whole hostname with a temporary owner/tester-only Cloudflare Access application before saving the route. Enable connector Access JWT validation. After the public release passes the launch checks, remove that temporary restriction and connector Access requirement together. The final public site uses app guest sessions.
  6. For a normal full Cloudflare DNS setup, saving the route creates the tunnel DNS entry. Check DNS has a proxied myverandah CNAME pointing to <TUNNEL_ID>.cfargotunnel.com. Resolve any existing record for that same name; keep unrelated website and email records. Do not add a conflicting A record to the server IP.

Current instructions: Tunnel setup, HTTP Host / Access settings, and temporary Access protection. If OTP is needed for the testers, add it explicitly under identity providers and allow only those tester emails.

Step 8
Verify HTTPS, private responses and operations

  • Visit https://myverandah.carekosh.com. Verify a valid browser certificate and no mixed-content warnings. Scope any HTTPS redirect to this hostname to avoid changing other Carekosh sites.
  • Keep /api/* and private generated files out of shared CDN caching. The app must send Cache-Control: private, no-store for sessions, jobs and private downloads. Remove any hostname-level Cache Everything rule that overrides this. Public sample assets may be cached separately.
  • Enable monitoring for app/worker/tunnel availability, CPU/RAM, queue size and disk usage. Implement automatic guest-file expiry and verified off-server backup of persistent projects and the database.

The public launch checklist

Complete these checks while the temporary staging gate is present. After removing it, repeat the anonymous browser, HTTPS and privacy checks from mobile data. A page loading successfully is only the first check.
